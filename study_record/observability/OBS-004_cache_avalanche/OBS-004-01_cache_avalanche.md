# OBS-004-01 缓存雪崩 / 击穿 / 穿透

> Redis 8.6.2 / 127.0.0.1:6379（2026-08-25 环境重建后全功能实例）
>
> 缓存的三类经典故障，名字像但机制完全不同：**穿透查不存在、击穿热点过期、雪崩大面积过期**。
> 所有数值均在本机实测（证据：`evidence/penetration.json`、`breakdown.json`、`avalanche.json`、`pg-mapping.json`）。

---

## 0. 一句话心法

> **穿透是"来了个不存在"，击穿是"热 key 恰好过期"，雪崩是"一片同时过期"。**
> 共同后果都是**回源打 DB**；治理口诀：穿透用布隆/空值，击穿用互斥锁，雪崩靠随机 TTL + 降级。

---

## 1. 三种故障模式速记

| 故障 | 触发 | 症状 | 治理 |
|---|---|---|---|
| **穿透** | 请求的 key 缓存/DB 都不存在 | 每次请求都打 DB，命中率骤降 | 空值缓存、布隆过滤器 |
| **击穿** | 某个**热点 key** 过期瞬间 | 大量并发同时回源重建 | 互斥锁（单飞） |
| **雪崩** | 大面积 key **同时过期** | DB 瞬时回源风暴 | TTL 随机化、多级缓存、降级 |

> 对照 PG 理解：穿透=查不存在的行（无效查询），击穿=热点行锁排队，雪崩=缓存表整体失效后的全表回源。

---

## 2. 缓存穿透：实测 + 两种治理

### 2.1 故障实测

```bash
# 模拟 10 万个"缓存和 DB 都不存在"的 key
(for i in $(seq 1 100000); do echo "GET user:$i"; done) \
  | redis-cli -h 127.0.0.1 -p 6379 -a 123456 --no-auth-warning -n 15 --pipe >/dev/null
```

实测 `INFO stats`：

```text
keyspace_misses : 1 → 100001
命中率          : 99.9999% → 89.6%
```

> 这类请求**永远无法命中**（key 不存在），每一次都穿透到 DB——攻击者构造随机 ID 就能把 DB 打挂。

### 2.2 治理 A：空值缓存

```bash
# 查询结果"不存在"也缓存 60 秒（值为空串）
SET user:99999 "" EX 60
GET user:99999        # 命中空值，不再打 DB（实测 TTL=60 正常生效）
```

> 注意：空值 TTL 要短（1~5 分钟），且只对"确实不存在"的结果缓存，避免长期占用内存。

### 2.3 治理 B：布隆过滤器（Redis bitmap 实测）

原理：把**所有存在的 ID** 写入一个位图，查询时先"预判"——不存在就拦下，存在才放行打 Redis/DB。

```python
# 两个 hash（crc32 / md5）取模 100000，写入 bf:user 位图
# 写入：SETBIT bf:user <h1> 1  /  SETBIT bf:user <h2> 1
# 查询：GETBIT 两个位，任一为 0 → 一定不存在
```

实测结果（1000 个真实 ID 写入）：

```text
已存在的 ID 1-1000   ：漏报 0/1000（绝不误杀）
不存在的 ID 1001-1200：误判 1/200 = 0.5%（可能误判、绝不漏报）
```

> **布隆过滤器特征：`可能在`（有误判）但 `一定不在`（零漏报）**——用它拦截不存在请求是安全的；
> 误判的代价只是"放行了少量请求去打 DB"，可通过调大位图/增加 hash 数降低误判率。

## 3. 缓存击穿：实测 + 互斥锁

### 3.1 故障实测（无锁）

热点 key `hot:item:1` 每 2 秒过期，8 个并发客户端同时 GET（3 轮）：

```text
round 1 → rebuild_count=8     ← 8 个并发全部 miss，全部去重建（打 DB 8 倍）
round 2 → rebuild_count=16
round 3 → rebuild_count=24
```

### 3.2 治理：互斥锁（单飞重建）

```bash
# 重建前先抢锁：只有抢到锁的 1 个客户端去查 DB 并写缓存，其余等待/重试
SET lock:hot:item:1 <token> NX EX 5     # 原子：抢锁 + 5 秒自动过期兜底
# 重建缓存后 DEL 锁
```

实测同场景：

```text
round 1 → rebuild_count=1   ← 每轮只有 1 个重建
round 2 → rebuild_count=2
round 3 → rebuild_count=3
```

**坑（实测）**：`SETNX key val EX 5` 会报 `ERR wrong number of arguments`——`SETNX` 是旧命令、**不支持 EX**；现代原子锁必须用 `SET key val NX EX n`（与 DAT-004 分布式锁联动）。

## 4. 缓存雪崩：实测 + TTL 随机化

### 4.1 故障实测：同一 TTL = 集中过期

1000 个 key 全部 `EX 5`，每秒采样 `expired_keys`：

```text
t=1s..6s : 11   （稳定，未到过期点）
t=7s     : 1011 （一秒内 +1000，1000 个 key 同一瞬间过期！）
```

→ DB 在 t=7s 瞬间收到 1000 个回源请求 = 雪崩。

### 4.2 治理：TTL 随机化

1000 个 key 改为 `EX random(3,12)`：

```text
t=4s:1012 → t=6s:1180 → t=8s:1440 → t=10s:1662 → t=12s:1857 → t=13s:2011
```

→ 同样的 1000 个过期，**摊平到 9 秒窗口**，DB 压力被削峰。

```python
# 典型做法：基础 TTL + 随机抖动
ttl = 3600 + random.randint(0, 600)   # 1 小时 ± 10 分钟
```

### 4.3 其他雪崩治理

- **多级缓存**：本地（进程内）+ Redis，Redis 挂/重建期间本地兜底；
- **热点续期**：热 key 不设绝对过期，后台异步刷新（永不过期 + 主动更新）；
- **限流/降级**：回源请求加锁或降级返回旧值，DB 打不挂优先。

## 5. 降级方案清单（生产落地）

```text
穿透 → 布隆过滤器（入口预判）+ 空值缓存（兜底）
击穿 → SET NX EX 互斥锁（单飞重建）
雪崩 → TTL 随机化 + 多级缓存 + 热点续期 + 限流降级
通用 → 熔断：DB 压力超阈值时降级返回（stale-while-revalidate）
```

## 6. 与 PG 对照

| Redis 场景 | PG 对应 | 治理对照 |
|---|---|---|
| 穿透（查不存在 key） | 无效查询/全表扫描 | 空值缓存/布隆 ≈ 预检查与物化视图 |
| 击穿（热点过期） | 热点行更新锁排队 | 互斥重建 ≈ PG advisory lock 串行化 |
| 雪崩（大面积过期） | 缓存整体失效全表回源 | TTL 随机化 ≈ 错峰任务调度 |
| 布隆过滤器（bitmap） | 位图索引/唯一索引预判 | 同思路：先过滤不存在 |

---

## 7. 小结

- **穿透**：命中率骤降是信号；治理=空值缓存 + 布隆过滤器（实测 0 漏报、0.5% 误判）；
- **击穿**：单点热点过期；治理=`SET NX EX` 互斥锁（实测 8 重建 → 1 重建）；
- **雪崩**：大面积同时过期；治理=TTL 随机化（实测 +1000/秒 → 摊平 9 秒）；
- 共同底线：**回源打 DB 要限流降级**，DB 不挂是最高优先级。
