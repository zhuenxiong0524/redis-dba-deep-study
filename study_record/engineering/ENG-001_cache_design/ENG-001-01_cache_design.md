# ENG-001-01 缓存架构设计与一致性

> Redis 8.6.2:6379 ↔ PG 18.4:54184（缓存场景表 `t_cache`）
>
> OBS-004 讲"缓存怎么挂"，本文讲"缓存怎么用才不挂"：**Cache-Aside 模式、双写一致性、连接池**。
> 所有时序实验均本机实测（证据：`evidence/cache-aside.json`、`consistency.json`、`connection-pool.json`、`pg-mapping.json`）。

---

## 0. 一句话心法

> **读走缓存、写走数据库，写完只删缓存不写缓存——让读路径自己重建，一致性由"先 DB 后删缓存"的时序保证。**
> 缓存的一致性不是靠"写两处"，而是靠"删一处、懒重建"。

---

## 1. 为什么需要缓存层（架构总览）

- **读多写少**是缓存适用的前提：把热数据放内存（Redis），DB 只承接写与缓存未命中；
- Cache-Aside（旁路缓存）是**最主流**模式：应用自己控制"先查缓存 → miss 查 DB → 写缓存"；
- 其他模式（Read-Through/Write-Through/Write-Behind）由缓存组件代管读写，适合封装层，本文聚焦 Cache-Aside。

---

## 2. Cache-Aside 读写流程（实测命令）

### 读路径（命中/未命中）

```bash
R="redis-cli -h 127.0.0.1 -p 6379 -a 123456 --no-auth-warning -n 5"
PG=/usr/local/pgsql/pgsql18.4/bin/psql

# 1) 先查缓存
v=$($R GET cache:user:1)
# 2) miss → 查 DB → 写缓存（带 TTL 兜底过期）
if [ -z "$v" ]; then
  v=$($PG -h 127.0.0.1 -p 54184 -d postgres -tAc "SELECT name FROM t_cache WHERE id=1")
  $R SET cache:user:1 "$v" EX 60
fi
```

### 写路径（只删缓存，不写缓存）

```bash
# 更新 DB
$PG -h 127.0.0.1 -p 54184 -d postgres -c "UPDATE t_cache SET name='alice-v4' WHERE id=1"
# 删除缓存（不是 SET 新值！）
$R DEL cache:user:1
```

> **心法：写操作"删缓存"而不是"写缓存"**——删掉后读路径必然重建新值；直接写缓存则要处理并发乱序（下一节的坑）。

---

## 3. 一致性竞态实测（核心）

用 PG `t_cache` + Redis `cache:user:1` 模拟四种写时序，观察 DB 与缓存是否一致：

### 场景 A：先写缓存（并发乱序）→ 不一致 ❌

```text
T1: DB 提交 v1 →（写缓存前卡 1.5s）
T2: DB 提交 v2(插队) → 缓存写入 v2
T1: 缓存写入 v1（覆盖！）
结果: DB=v2  缓存=v1  不一致
```

**教训**：先写缓存的方案在"DB 提交顺序 ≠ 缓存写顺序"时必脏，且无法简单修复。

### 场景 B：先删缓存再写 DB（读插入旧值）→ 不一致 ❌

```text
T: 删除缓存 →（写 DB 前卡 0.8s）
R: 读 miss → 读 DB 旧值 v2 → 缓存写回 v2
T: DB 更新为 v3
结果: DB=v3  缓存=v2  不一致
```

**教训**：删缓存到写 DB 之间有个窗口，读请求会把旧值塞回缓存（经典竞态）。

### 场景 C：Cache-Aside 标准（先 DB 后删缓存）→ 一致 ✅

```text
T: DB 更新为 v4 完成 → DEL 缓存
R: miss → 读 DB 得 v4 → 写缓存 v4
结果: DB=v4  缓存=v4  一致
```

**为什么对**：删除发生在 DB 提交**之后**，之后任何重建读到的都是已提交的新值；DB 提交前的旧读只会写回旧值，但随后被 DEL 清掉。

### 场景 D：延迟双删（场景 B 的兜底）→ 一致 ✅

```text
T: 删缓存 → DB 更新 v5（慢）
R: 竞态插入旧值 v4
T: 完成后延迟二次删除缓存（如 1s）
结果: DB=v5  缓存=空 → 下次读重建 v5
```

> 延迟双删适用"必须先删缓存再写 DB"的存量系统；延迟时长要 **> 读请求写回缓存的最长耗时**，否则二次删除仍可能早于旧值写回。

## 4. 一致性方案全景（按强度排序）

| 方案 | 做法 | 一致性 | 成本 |
|---|---|---|---|
| Cache-Aside（删缓存） | 先 DB 后删缓存 | 最终一致（绝大多数时序正确） | 低，推荐默认 |
| 延迟双删 | 删缓存 → DB → 延迟再删 | 覆盖极端竞态 | 中，延迟参数难定 |
| 版本号/比对 | 缓存带版本，写入比对 | 强一点 | 中，应用改造 |
| 订阅 binlog/CDC | 监听 DB 变更自动失效缓存 | 解耦、可靠 | 高，引入消息组件 |
| 强一致兜底 | 关键数据不缓存或短 TTL | 强 | 放弃缓存收益 |

> 生产组合拳：**默认 Cache-Aside + 热点/敏感数据短 TTL + 变更订阅兜底**；能容忍最终一致是缓存的前提，强一致场景不缓存。

## 5. 连接池与客户端（实测）

### 5.1 有连接池 vs 无连接池

```bash
# 有池：20 个常驻连接（管道保持），INFO clients 实测
connected_clients: 21   # 20 池连接 + 1 采样连接，稳定不复用开销

# 无池：300 次 redis-cli 短连接（每请求新建）
ss -tan | grep -c TIME-WAIT   # 实测 422 个 TIME-WAIT 堆积
```

- 无池代价：每次请求 = TCP 握手 + Redis 认证 + 挥手 → 延迟与 TIME_WAIT 堆积，高 QPS 下雪崩；
- 有池收益：连接复用，`connected_clients` 稳定在池大小附近，QPS 高低都不波动。

### 5.2 连接池关键参数（客户端库通用）

```text
maxActive     最大并发连接（≈ 期望 QPS × 单连接吞吐）
maxIdle/minIdle 空闲连接上下限（避免频繁建连/占资源）
maxWait       池满时等待上限（超时快速失败，别无限排队）
socketTimeout 单命令超时（结合 OBS-002 延迟定位）
健康检查      定期 PING，剔除坏连接
```

> **心法：连接池大小不是越大越好**——Redis 单线程，太多并发连接只是排队；按"期望 QPS ÷ 单连接吞吐"估算即可。

## 6. 与 PG 对照

| Redis | PG | 说明 |
|---|---|---|
| Cache-Aside（删缓存） | 物化视图刷新/应用缓存 | 写路径旁路读缓存 |
| 双写一致性竞态 | MVCC+行锁串行化 | Redis 无事务化缓存写，靠时序约定+兜底 |
| 延迟双删 | 延迟触发式视图刷新 | 异步一致思路 |
| 连接池（20 常驻） | PgBouncer / 应用连接池 | PG 每连接一进程更重，池收益更大 |
| TTL 过期失效 | 无直接对应 | 缓存侧特有的最终一致机制 |

---

## 7. 小结

- **Cache-Aside 是默认姿势**：读走缓存、写走 DB、写完删缓存；实测场景 C 一致、A/B 不一致；
- **一致性靠时序**：先 DB 后删缓存 > 先删缓存后 DB > 先写缓存；极端竞态用延迟双删/CDC 兜底；
- **连接池**：复用连接避免握手开销，实测 20 常驻连接稳定 vs 300 短连接堆积 422 个 TIME-WAIT；
- 能容忍最终一致是缓存的前提，强一致数据不缓存或短 TTL。
